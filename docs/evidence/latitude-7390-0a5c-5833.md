# Latitude 7390 / BCM5880 `0a5c:5833` bring-up evidence

This is a privacy-safe summary derived from local hardware observations. Raw
USB payloads, device-node identifiers, process identifiers, timestamps, and
complete runtime logs are intentionally excluded.

## Test environment

- Distribution family: Arch Linux
- Laptop: Dell Latitude 7390
- Device family: Broadcom BCM5880 / ControlVault2
- USB ID: `0a5c:5833`

Interface 0 exposed the transport endpoints also seen on `0a5c:5834`:

```text
0x01  bulk OUT
0x81  bulk IN
0x85  interrupt IN
```

Endpoint equality was treated as an initial compatibility indicator, not as
proof of full protocol equivalence.

## Staged transport result

The transfer-free enumeration and claim/release-only stages completed. One
explicitly allow-listed `cv_get_ush_ver` (`0x39`) request then produced:

- a complete 44-byte write;
- an interrupt completion reply;
- a 44-byte bulk response carrying command ID `0x39`;
- no timeout or crash.

The raw request and response payloads are not published.

## Enrollment research result

Later repository-local experiments established:

- `0x89 → 0x8a → new capture` recovery works on the tested device.
- A bounded second UpdateEnrollment after `0x59` returns native `0x89`.
- That transition allows accepted progress to continue beyond the former
  three-sample boundary.
- Completion remains zero and the host stage counter can exceed ten.
- State 2, template commit, and verification have not been reached.

The bounded `0x59` behavior is a diagnostic hypothesis, not a completed
driver fix.

A later Windows A21 reference run successfully enrolled on the same device.
Its privacy-safe structural trace contained four accepted `0x6c` operations,
then two `0x6e` operations with differently sized replies, and no visible
`0x6f` application-message header. See
`windows-a21-enrollment-runtime.md`. Static comparison later showed that the
two commits are separate completion and formal-finalization phases with
different argument construction; see
`windows-a21-double-commit-static.md`. This shifts the immediate comparison to
the Windows and Linux initialization/capture inputs that precede `0x6c`, plus
device/session state across the two commits. Static ABI recovery shows no
host pointer handoff: both reuse the same input token, while only the first
requests a large returned blob.

Two independent failed Windows controls each accepted three `0x6c` replies,
returned a shorter protected reply for the fourth, and discarded through
`0x6d`. A third control accepted one update before the device reset from
`0a5c:5833` to the single-interface `0a5c:5831` identity. A standard USB reset
did not change that identity; a complete host power-off restored `5833` and
all interfaces without a device problem. These controls are structural
evidence only: protected Windows replies do not prove a numeric mapping to
Linux status `0x59`.

A later one-attempt Linux fresh-boundary control reached accepted progress
`1/10`. Its structural trace was `0x8a`, capture `0x66`, rejected update
`0x6c`, recovery `0x8a`, capture `0x66`, accepted incomplete update `0x6c`,
then a fresh `0x66`. The stock state machine did not send `0x8a` between the
accepted update and the final capture. Four lift-and-touch attempts produced
no further completed capture. Cancellation emitted `0x68`; no commit-family
`0x6e` or `0x6f` was observed. The capture had zero packet drops and the
device remained `0a5c:5833`.

The first follow-up control with accepted-incomplete re-arm enabled returned
native `0x89` for all five attempted samples. Each ordinary bad-capture
recovery successfully issued `0x8a` and a fresh `0x66`; the new
status-zero/completion-zero branch was therefore not exercised. Explicit
cancellation completed through `0x68`, two `0x6d` operations, and close
`0x04`. The USB capture reported zero drops and the device remained `5833`.

The second follow-up control obtained three accepted status-zero/completion-zero
updates. Each was followed by the experimental native `0x8a`; all three
following fresh `0x66` captures completed, unlike the earlier no-re-arm hang.
After the three accumulated accepted updates, the next fresh `0x6c` returned
native `0x59`. The policy preserved the status without replay or synthetic
completion, did not reach `0x6e` or `0x6f`, and allowed normal cleanup and
device close. The capture contained 378 packets with zero drops, and the
device remained enumerated as `0a5c:5833`.

The capture-continuation effect of re-arm and the fourth-update `0x59` boundary
are therefore independent in these runs. Future comparison should focus on the
Windows and Linux initialization, capture input, and accumulated state
preceding the fourth `0x6c`, not on another same-update retry.

An independent run on 2026-08-19 reproduced the same boundary. Four native
`0x89` quality retries were interleaved with three accepted
status-zero/completion-zero updates. Every retry and accepted-incomplete update
was followed by successful native `0x8a`, and every following fresh capture
completed. The eighth update returned native `0x59`; the fail-closed policy
preserved it and exited through normal cleanup without replay or commit.

The associated USB trace contained eight `0x66`, eight `0x6c`, and eight
`0x8a` request/response pairs. Three update replies had the 96-byte
accepted-progress shape and five had the 44-byte non-success shape. All 318
packets were captured with zero drops, cleanup closed the device, and it
remained enumerated as `0a5c:5833`. The private redacted log and PCAP hashes are
`3ad3895e260785284371c11bdde690fe4e631528649411a58cd38c7ff1488f02` and
`f410f096607fa57a1d629d2bd9063872be05e3605eb5c1a82e2c82cdc6a3ee24`.

Immediately before that replication, a separate two-finger control with
explicit lift cycles produced sixteen consecutive native `0x89` results. Each
normal re-arm and fresh capture succeeded, then explicit cancellation and
close completed cleanly. Its 560-packet capture had zero drops and contained
seventeen `0x66`, sixteen `0x6c`, and seventeen `0x8a` request/response pairs.
The private redacted-log and PCAP hashes are
`7bcba1210bfc8a14a580d03d5d15f38d281d905d9975ee3a4fdb17753ff8aae7` and
`e76771ce71be04a785047ba4b8c46e53d6820220aff3f717ca5fd0c9472cbbb8`.

## Privacy statement

No raw fingerprint features, biometric templates, enrollment tokens, capture
payloads, device serial numbers, user identifiers, or authentication
credentials are retained in this record.

## Conclusion

Probe, open, capture, and bounded retry recovery work on the tested BCM5880
device. Enrollment completion, template commit, and verification remain
incomplete.
